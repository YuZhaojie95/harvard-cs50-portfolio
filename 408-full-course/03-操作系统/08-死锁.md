## 🚪 课前引入

一条窄窄的单行桥，两辆车从桥的两头同时开上来，在桥中间**迎面相遇**：
- 车 A 占着桥的左半段，要前进必须等车 B 让出右半段
- 车 B 占着桥的右半段，要前进必须等车 A 让出左半段
- 谁都不肯（也不能）后退——**永远僵持**

这就是**死锁**。上节课的哲学家问题中，5 个人各拿一根左筷子、等右筷子，也是死锁。

## 一、死锁的概念（⭐⭐）

### 📐 定义
**死锁**：多个进程因**竞争资源**而造成的一种**互相等待**的僵局，若无外力作用，这些进程都将**无法向前推进**。

### 📐 死锁、饥饿、死循环的区别
| | 死锁 | 饥饿 | 死循环 |
|---|---|---|---|
| 含义 | 各进程**互相等待**对方手里的资源 | 进程**长期得不到**想要的资源（如 SJF 中的长作业） | 进程执行过程中一直跳不出某个循环 |
| 涉及进程数 | **至少 2 个** | 可以只有 **1 个** | 可以只有 1 个 |
| 进程状态 | 都处于**阻塞态** | 可能是**阻塞态**（等 I/O），也可能是**就绪态**（等 CPU） | 可以是**运行态** |
| 原因 | OS 资源分配问题 | OS 资源分配策略不公平 | **程序员的代码逻辑问题** |

### 📐 死锁产生的原因
1. **系统资源的竞争**：系统中的**不可剥夺资源**（如打印机、磁带机）数量不足以满足多个进程的需要。（对**可剥夺资源**，如 CPU、主存，的竞争不会引起死锁）
2. **进程推进顺序非法**：进程在运行过程中，**请求和释放资源的顺序不当**
   - 例：P1 占 R1 请求 R2，P2 占 R2 请求 R1
   - 信号量使用不当也会造成死锁（如生产者-消费者中 P 操作顺序颠倒）

## 二、死锁的四个必要条件（⭐⭐⭐）

产生死锁**必须同时满足**以下四个条件，**只要其中任一条件不成立，死锁就不会发生**：

1. **互斥条件**：进程对所分配到的资源进行**排他性**使用，即在一段时间内某资源仅为一个进程所占有
   - 🧒 桥一次只能过一辆车
2. **不剥夺条件（不可抢占）**：进程所获得的资源在**未使用完之前，不能被其他进程强行夺走**，只能由获得该资源的进程**自己主动释放**
   - 🧒 不能用吊车把对面的车吊走
3. **请求并保持条件**：进程**已经保持了至少一个资源**，但又提出了**新的资源请求**，而该资源已被其他进程占有，此时请求进程被阻塞，但对自己已获得的资源**保持不放**
   - 🧒 车 A 占着左半段，又想要右半段，同时不肯退出左半段
4. **循环等待条件**：存在一种进程**资源的循环等待链**，链中每个进程已获得的资源同时被链中下一个进程所请求
   - 🧒 A 等 B，B 等 A（或 A 等 B 等 C 等 A）

⚠️ **循环等待是死锁的必要条件，但不是充分条件**：
- 若每类资源**只有 1 个**，则资源分配图中的环路是死锁的**充分必要条件**
- 若某类资源**有多个**，有环路**不一定**死锁（环外的进程可能释放资源打破僵局）

## 三、死锁的处理策略总览（⭐⭐）

| 策略 | 思路 | 资源分配策略 | 主要方法 | 优点 | 缺点 |
|---|---|---|---|---|---|
| **死锁预防** | **破坏四个必要条件之一**，让死锁**不可能**发生 | **保守**，宁可资源闲置 | 一次请求所有资源、资源剥夺、**资源有序分配** | 适用于突发式处理的进程，不必进行剥夺 | 效率低，进程初始化时间长；剥夺次数过多；不便灵活申请新资源 |
| **死锁避免** | 在资源**动态分配**过程中，用算法防止系统进入**不安全状态** | 介于预防和检测之间 | **银行家算法**（寻找可能的安全序列） | 不必进行剥夺 | 必须知道将来的资源需求；进程不能被长时间阻塞 |
| **死锁检测与解除** | **允许**死锁发生，定期检测，发现后**解除** | **宽松**，只要允许就分配 | 定期检查死锁是否已经发生 | 不延长进程初始化时间，允许对死锁进行现场处理 | 通过剥夺解除死锁，造成损失 |
| **鸵鸟策略** | 忽略死锁（认为发生概率很低） | —— | —— | 简单 | —— |

## 四、死锁预防（⭐⭐）

### 📐 1. 破坏互斥条件
把只能互斥使用的资源改造为**允许共享**使用。
- 例：**SPOOLing 技术**把独占的打印机改造成逻辑上的共享设备
- ❌ 很多资源本身就**不能**改造为共享（互斥是资源本身的特性），**不太可行**

### 📐 2. 破坏不剥夺条件
- 方案一：当某个进程请求新的资源**得不到满足**时，必须**立即释放**已保持的所有资源，以后需要时再重新申请
- 方案二：当某个进程需要的资源被其他进程占有时，可以由 OS 协助，**将想要的资源强行剥夺**（一般考虑优先级）
- ❌ 实现复杂；释放已获得的资源可能造成**前一阶段工作的失效**，只适用于**易于保存和恢复状态**的资源（如 **CPU**、内存），**不适用于打印机**
- ❌ 反复申请和释放资源会增加系统开销，降低吞吐量；可能导致**饥饿**

### 📐 3. 破坏请求并保持条件
**静态分配方法**：进程在**运行前一次性申请完它所需要的全部资源**，在资源未满足前不让它投入运行。一旦投入运行，这些资源就一直归它所有，不再提出其他资源请求。
- ✅ 实现简单
- ❌ **资源严重浪费**：有些资源可能只在运行初期或快结束时才用，甚至根本不用
- ❌ 可能导致某些进程**饥饿**

### 📐 4. 破坏循环等待条件（⭐⭐）
**顺序资源分配法**：给系统中的资源**编号**，规定每个进程**必须按编号递增的顺序请求资源**，同类资源（编号相同）一次申请完。
- 原理：一个进程只有已占有**小编号**的资源时，才有资格申请**更大编号**的资源。持有大编号资源的进程不可能逆向回来申请小编号资源，所以**不会形成环路**
- 🧒 哲学家问题中，“奇数号先拿左、偶数号先拿右”其实就是一种有序分配的思想
- ❌ 编号必须相对稳定，限制了新类型设备的增加
- ❌ 进程实际使用资源的顺序可能与编号顺序不一致，造成资源浪费
- ❌ 给用户编程带来麻烦

## 五、死锁避免：银行家算法（⭐⭐⭐）

### 📐 安全状态与安全序列
- **安全序列**：如果系统按照这个序列 P1, P2, …, Pn 分配资源，**每个进程都能顺利完成**，那么这个序列就是安全序列
- **安全状态**：系统中存在**至少一个**安全序列
- **不安全状态**：找不到任何一个安全序列

⚠️ 关键结论：
- 系统处于**安全状态**，**一定不会**发生死锁
- 系统进入**不安全状态**，**可能**会发生死锁（**不一定**，因为进程可能提前释放资源、或不会用到声明的最大需求）
- **死锁一定是不安全状态**
- 死锁避免的思想：**在分配资源之前，预先判断这次分配是否会导致系统进入不安全状态**，若会，则**不分配**，让进程等待

🧒 **比喻：银行放贷**
- 银行有 10 亿元，三个企业分别**最多**要借 7 亿、4 亿、9 亿，目前已借出 2、2、3 亿，银行剩 3 亿
- 银行要判断：如果再借给某个企业，会不会出现“**所有企业都还没借够、没法完工还钱，而银行也没钱了**”的局面？
- 如果能找到一个顺序，让企业一个个借够、完工、还钱，那就是安全的

### 📐 银行家算法的数据结构
设系统中有 n 个进程、m 类资源：
| 数据结构 | 含义 |
|---|---|
| **Available[m]** | 可利用资源向量：每类资源**当前可用**的数目 |
| **Max[n][m]** | 最大需求矩阵：每个进程对每类资源的**最大需求** |
| **Allocation[n][m]** | 分配矩阵：每个进程**已分配**的每类资源数 |
| **Need[n][m]** | 需求矩阵：每个进程**还需要**的每类资源数 |

📐 **Need = Max − Allocation**（第一步往往就是算这个！）

### 📐 银行家算法（资源请求算法）
进程 Pi 发出请求向量 Request_i：
1. 若 **Request_i ≤ Need_i**，转步骤 2；否则**出错**（请求超过了它声明的最大需求）
2. 若 **Request_i ≤ Available**，转步骤 3；否则 Pi 须**等待**（资源不够）
3. **试探着**把资源分配给 Pi，修改数据结构：
   ```
   Available = Available − Request_i
   Allocation_i = Allocation_i + Request_i
   Need_i = Need_i − Request_i
   ```
4. 执行**安全性算法**，检查此次分配后系统是否处于安全状态：
   - 若**安全**，**正式分配**
   - 若**不安全**，**作废**本次试探分配，恢复原来的状态，让 Pi **等待**

### 📐 安全性算法
1. 初始化：工作向量 **Work = Available**；Finish[i] = false
2. 从进程集合中找一个满足 **Finish[i] = false 且 Need_i ≤ Work** 的进程：
   - 找到：该进程可以顺利完成并**释放**它所占有的全部资源：**Work = Work + Allocation_i**，Finish[i] = true，把 Pi 加入安全序列，**重复步骤 2**
   - 找不到：转步骤 3
3. 若所有 Finish[i] 都为 true，系统处于**安全状态**；否则不安全

⚠️ **释放的是 Allocation（已分配的），不是 Need 或 Max**！进程完成后，归还它手上所有的资源。

### ✏️ 例（经典题）
系统有 5 个进程 P0~P4，3 类资源 A、B、C（总数 10、5、7）。T0 时刻状态：

| 进程 | Max (A B C) | Allocation (A B C) | Need (A B C) |
|---|---|---|---|
| P0 | 7 5 3 | 0 1 0 | **7 4 3** |
| P1 | 3 2 2 | 2 0 0 | **1 2 2** |
| P2 | 9 0 2 | 3 0 2 | **6 0 0** |
| P3 | 2 2 2 | 2 1 1 | **0 1 1** |
| P4 | 4 3 3 | 0 0 2 | **4 3 1** |

Available = (10, 5, 7) − (7, 2, 5) = **(3, 3, 2)**

**(1) T0 时刻是否安全？**

| 步骤 | 选中的进程 | Need ≤ Work？ | Work + Allocation = 新 Work |
|---|---|---|---|
| 1 | **P1** | (1,2,2) ≤ (3,3,2) ✓ | (3,3,2) + (2,0,0) = **(5,3,2)** |
| 2 | **P3** | (0,1,1) ≤ (5,3,2) ✓ | (5,3,2) + (2,1,1) = **(7,4,3)** |
| 3 | **P4** | (4,3,1) ≤ (7,4,3) ✓ | (7,4,3) + (0,0,2) = **(7,4,5)** |
| 4 | **P0** | (7,4,3) ≤ (7,4,5) ✓ | (7,4,5) + (0,1,0) = **(7,5,5)** |
| 5 | **P2** | (6,0,0) ≤ (7,5,5) ✓ | (7,5,5) + (3,0,2) = **(10,5,7)** |

存在安全序列 **{P1, P3, P4, P0, P2}**，系统处于**安全状态**。（安全序列不唯一，如 {P1, P3, P4, P2, P0} 也是。）

**(2) P1 请求 (1, 0, 2)，能否分配？**
1. Request (1,0,2) ≤ Need_1 (1,2,2) ✓
2. Request (1,0,2) ≤ Available (3,3,2) ✓
3. 试分配：Available = (2,3,0)，Allocation_1 = (3,0,2)，Need_1 = (0,2,0)
4. 安全性检查：P1 (0,2,0) ≤ (2,3,0) → Work = (5,3,2)；P3 → (7,4,3)；P4 → (7,4,5)；P0 → (7,5,5)；P2 → (10,5,7)
   → 安全序列 {P1, P3, P4, P0, P2}，**可以分配**

**(3) 在 (2) 之后，P0 请求 (0, 2, 0)，能否分配？**
1. (0,2,0) ≤ Need_0 (7,4,3) ✓
2. (0,2,0) ≤ Available (2,3,0) ✓
3. 试分配：Available = **(2,1,0)**，Need_0 = (7,2,3)
4. 安全性检查：
   - P0 Need (7,2,3)，P1 (0,2,0)，P2 (6,0,0)，P3 (0,1,1)，P4 (4,3,1)
   - 与 Work = (2,1,0) 比较：P1 的 B 需要 2 > 1；P3 的 C 需要 1 > 0；其余更不满足
   - **找不到任何进程**能完成 → **不安全**
   → **不能分配**，P0 等待

📝 **真题（2020 年第 27 题）**：某系统中有 A、B 两类资源各 6 个，t 时刻资源分配及需求情况如下表所示：

| 进程 | A 已分配数量 | B 已分配数量 | A 需求总量 | B 需求总量 |
|---|---|---|---|---|
| P1 | 2 | 3 | 4 | 4 |
| P2 | 2 | 1 | 3 | 1 |
| P3 | 1 | 2 | 3 | 4 |

t 时刻安全性检测结果是：A. 存在安全序列 P1、P2、P3　B. 存在安全序列 P2、P1、P3　C. 存在安全序列 P2、P3、P1　D. 不存在安全序列

1. ⚠️ 表中给的是“**需求总量**”（= Max），先算 Need：P1 (2,1)，P2 (1,0)，P3 (2,2)
2. Available = (6 − 5, 6 − 6) = **(1, 0)**
3. 只有 P2 的 Need (1,0) ≤ (1,0) → P2 完成，Work = (1,0) + (2,1) = (3,1)
4. P1 (2,1) ≤ (3,1) ✓ → Work = (5,4)；P3 (2,2) ≤ (5,4) ✓ → Work = (6,6)
5. 安全序列 **P2、P1、P3** → 选 **B**
   - C 不对：P2 之后 Work = (3,1)，P3 需要 (2,2)，B 类不够

📝 **真题（2022 年第 26 题）**：系统中有三个进程 P0、P1、P2 及三类资源 A、B、C。若某时刻系统分配资源的情况如下表所示，则此时系统中存在的安全序列的个数为：A. 1　B. 2　C. 3　D. 4

| 进程 | 已分配 (A B C) | 尚需 (A B C) | 可用 (A B C) |
|---|---|---|---|
| P0 | 2 0 1 | 0 2 1 | 1 3 2 |
| P1 | 0 2 0 | 1 2 3 | |
| P2 | 1 0 1 | 0 1 3 | |

- 第一个能执行的进程：P0 (0,2,1) ≤ (1,3,2) ✓；P1 (1,2,**3**) C 类 3 > 2 ✗；P2 (0,1,**3**) C 类 3 > 2 ✗
- **只能 P0 先**，之后 Work = (1,3,2) + (2,0,1) = (3,3,3)
- P1 (1,2,3) ≤ (3,3,3) ✓，P2 (0,1,3) ≤ (3,3,3) ✓，两者都能执行，且执行任一后资源只会更多，另一个也能执行
- 安全序列：**P0, P1, P2** 和 **P0, P2, P1**，共 **2** 个 → 选 **B**

## 六、死锁的检测与解除（⭐⭐）

### 📐 资源分配图
- **圆圈**表示**进程**，**方框**表示一类**资源**，方框中的**小圆点**表示该类资源的一个实例
- **请求边**：进程 → 资源（进程在请求一个该资源）
- **分配边**：资源（中的某个圆点）→ 进程（已分配给该进程）

```
      ┌───┐                       ┌───┐
      │ ● │ ────分配边────►  P1 ──请求边──► │ ● │
      │ ● │                                │   │
      └───┘ R1                             └───┘ R2
```

### 📐 资源分配图的简化
1. 在资源分配图中，找出**既不阻塞又不是孤点**的进程 Pi：它的所有**请求边**所请求的资源都有足够的**空闲**资源可以满足
2. 让 Pi 执行完，**释放**它的所有资源：**消去它所有的请求边和分配边**，使之成为**孤立结点**
3. 被释放的资源可能使其他阻塞的进程变得可以执行，**重复**上述过程

### 📐 死锁定理（⭐⭐）
- 若资源分配图能被**完全简化**（所有的边都能被消去），则系统**没有死锁**
- 若**不能完全简化**，则系统**发生了死锁**；仍连着边的那些进程就是**死锁进程**
- 简化的结果与简化顺序**无关**

### 📐 死锁检测算法
与安全性算法类似，但使用的是**当前的请求 Request**（而不是 Need）：
1. Work = Available；对 Allocation 不为 0 的进程，Finish = false
2. 找一个 Finish = false 且 **Request ≤ Work** 的进程，Work += Allocation，Finish = true；重复
3. 若最后还有 Finish = false 的进程，这些进程**处于死锁**

### 📐 死锁解除
1. **资源剥夺法**：**挂起**某些死锁进程，**抢占**它的资源，分配给其他死锁进程。但应防止被挂起的进程长时间得不到资源而饥饿
2. **撤销进程法（终止进程法）**：强制**撤销部分甚至全部**死锁进程，并剥夺它们的资源。实现简单，但代价可能很大（有些进程运行了很久，一撤销前功尽弃）
3. **进程回退法**：让一个或多个死锁进程**回退**到足以避免死锁的地步。要求系统保存进程的历史信息，设置**还原点**

选择撤销哪个进程时考虑：进程优先级、已执行多长时间、还要多久完成、已使用了多少资源、是交互式还是批处理……

## 七、不发生死锁的最少资源数（⭐⭐⭐ 必考计算）

### 📐 问题
系统中有 n 个进程，第 i 个进程**最多**需要 kᵢ 个某类资源。**该类资源至少要有多少个，才能保证不会发生死锁？**

### 📐 思路：考虑“最坏情况”
最倒霉的情况：**每个进程都拿到了 (kᵢ − 1) 个资源**，都还差 1 个，此时资源恰好分完——**死锁**！
只要在此基础上**再多 1 个资源**，就能让某个进程拿到最后一个而完成，完成后释放资源，其他进程也能依次完成。

📐 **公式**：
```
最少资源数 = Σ(kᵢ − 1) + 1
```
- 若每个进程都需要 k 个：**最少资源数 = n(k − 1) + 1**

📝 **真题（2021 年第 31 题）**：若系统中有 n（n ≥ 2）个进程，每个进程均需要使用某类临界资源 2 个，则系统不会发生死锁所需的该类资源总数至少是：A. 2　B. n　C. n + 1　D. 2n
- n × (2 − 1) + 1 = **n + 1** → 选 **C**

✏️ **例 1**：3 个进程，每个进程最多需要 4 台打印机，至少要多少台才不会死锁？
- 3 × (4 − 1) + 1 = **10** 台

✏️ **例 2（反问）**：系统有 **11** 台打印机，N 个进程共享，每个进程最多需要 **3** 台。N 最大为多少时系统不会死锁？
- 要求 N × (3 − 1) + 1 ≤ 11 → 2N ≤ 10 → **N ≤ 5**

✏️ **例 3**：某系统有 m 个同类资源供 n 个进程共享，若每个进程最多申请 k 个（k ≤ m），则不会死锁的条件是？
- **n(k − 1) + 1 ≤ m**，即 n(k − 1) < m

---

## ⚠️ 易错点

1. 死锁至少涉及 **2 个**进程，都处于**阻塞态**；饥饿可以只有 1 个进程
2. 四个必要条件：**互斥、不剥夺、请求并保持、循环等待**；缺一不可
3. **有环不一定死锁**（资源有多个实例时）；每类资源只有一个时，有环 = 死锁
4. **预防**是破坏必要条件；**避免**是用银行家算法防止进入不安全状态
5. **安全状态一定不死锁；不安全状态不一定死锁**
6. 银行家算法：**先算 Need = Max − Allocation**；安全检查时 **Work 加的是 Allocation**
7. 题目给的是“需求总量/最大需求”还是“尚需”，一定看清
8. 死锁检测用的是 **Request**，银行家算法用的是 **Need**
9. 最少资源数 = **Σ(kᵢ − 1) + 1**
10. SPOOLing 破坏**互斥**条件；资源有序分配破坏**循环等待**条件；一次性分配破坏**请求并保持**条件

## 📋 本课小结

| 知识点 | 要点 |
|---|---|
| 死锁 | 多进程互相等待、无法推进 |
| 必要条件 | 互斥、不剥夺、请求并保持、循环等待 |
| 预防 | 破坏条件：SPOOLing、剥夺、一次性分配、有序分配 |
| 避免 | 银行家算法：Need = Max − Alloc；找安全序列 |
| 检测 | 资源分配图简化；不能完全简化则死锁 |
| 解除 | 剥夺资源、撤销进程、进程回退 |
| 最少资源数 | Σ(kᵢ − 1) + 1 |

## 🏋️ 课后练习

1. 某系统有 4 个进程，分别最多需要 2、3、4、5 个同类资源，至少需要多少个该类资源才能保证不死锁？
2. 系统中有 3 个进程，每个进程最多需要 2 个同类资源。系统至少有几个资源才不会死锁？若系统只有 3 个资源，会不会死锁？
3. 判断：(a) 系统处于不安全状态一定会死锁；(b) 破坏“请求并保持”条件可以采用一次性分配所有资源的方法；(c) 资源分配图中有环，则一定死锁。
4. 系统有 A、B、C 三类资源，Available = (1, 1, 2)。P0：Allocation (1,0,0)，Need (2,1,1)；P1：Allocation (0,1,1)，Need (1,0,2)；P2：Allocation (1,1,0)，Need (0,1,2)。判断是否安全，若安全，给出一个安全序列。
5. 为什么说“剥夺资源”的预防方法不适用于打印机？

<details>
<summary>📖 答案</summary>

1. (2−1) + (3−1) + (4−1) + (5−1) + 1 = 1 + 2 + 3 + 4 + 1 = **11**
2. 3 × (2 − 1) + 1 = **4**；3 个资源时**可能死锁**（每个进程各拿 1 个，都在等第 2 个）
3. (a) **错**，可能死锁；(b) **对**；(c) **错**，资源有多个实例时有环不一定死锁
4. Work = (1,1,2)：P1 Need (1,0,2) ≤ (1,1,2) ✓ → Work = (1,2,3)；P2 Need (0,1,2) ≤ (1,2,3) ✓ → Work = (2,3,3)；P0 Need (2,1,1) ≤ (2,3,3) ✓ → Work = (3,3,3)。**安全**，安全序列 **{P1, P2, P0}**
5. 打印机正在打印时若被剥夺给其他进程，前一个进程的打印内容与后一个进程的内容会混在一起，前一阶段的工作失效；打印机的状态不易保存和恢复
