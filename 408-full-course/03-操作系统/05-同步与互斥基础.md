## 🚪 课前引入

两个人同时往同一个银行账户存钱，账户原有 **100 元**：
- 甲存 50 元：读余额 100 → 算出 150 → 写回 150
- 乙存 30 元：读余额 100 → 算出 130 → 写回 130

如果两人**交替**进行：
```
甲：读余额 = 100
乙：读余额 = 100
甲：写回 150
乙：写回 130      ← 甲存的 50 元“消失”了！
```
最终余额 130，而正确答案是 180。

这就是**并发访问共享数据**带来的问题——结果取决于执行的**先后顺序**（叫**竞争条件**）。

对应到程序：
```c
count++;    // 看起来是一条语句，实际是 3 条机器指令：
            // ① mov eax, [count]    读
            // ② add eax, 1          改
            // ③ mov [count], eax    写
```
两个进程并发执行 count++，如果在 ① 和 ③ 之间被打断切换，就可能丢失一次加法。

**解决办法**：让“读-改-写”这一段代码**同一时刻只能有一个进程执行**——这就是**互斥**。

## 一、基本概念（⭐⭐）

### 📐 临界资源
**一次仅允许一个进程使用的资源**称为**临界资源**。
- 物理设备：打印机、磁带机
- 软件资源：**共享变量**、共享数据结构、共享缓冲区

### 📐 临界区
进程中**访问临界资源的那段代码**称为**临界区**（Critical Section）。

为了保证临界资源被正确使用，把访问临界资源的过程分成 4 个部分：
```c
do {
    entry section;       // 进入区：检查能否进入临界区，若能，则设置“正在访问”标志（上锁）
    critical section;    // 临界区：访问临界资源的代码
    exit section;        // 退出区：清除“正在访问”标志（解锁）
    remainder section;   // 剩余区：其余代码
} while (true);
```
⚠️ **临界区是代码**，临界资源是资源。“进入区”和“退出区”是负责实现**互斥**的代码。

### 📐 同步（直接制约关系）
**同步**：为完成某种任务而建立的两个或多个进程，这些进程因为需要在某些位置上**协调它们的工作次序**而产生的制约关系。
- 🧒 **接力赛**：第二棒必须等第一棒跑到才能出发——有**先后顺序**的要求
- 例：进程 A 负责输入数据到缓冲区，进程 B 从缓冲区取数据计算。缓冲区空时 B 必须等 A 放入；缓冲区满时 A 必须等 B 取走

### 📐 互斥（间接制约关系）
**互斥**：当一个进程进入临界区使用临界资源时，另一个进程**必须等待**；当占用临界资源的进程退出临界区后，另一进程才允许去访问此临界资源。
- 🧒 **单人卫生间**：有人在里面时，其他人必须在门外等；谁先谁后无所谓，但**不能同时**进去
- 源于**资源共享**

| | 同步 | 互斥 |
|---|---|---|
| 关系 | **直接**制约（进程之间合作） | **间接**制约（因共享资源） |
| 要求 | 按一定**顺序**执行 | **不能同时**访问，顺序不限 |

### 📐 实现临界区互斥必须遵循的 4 条准则（⭐⭐⭐）
1. **空闲让进**：临界区空闲时，可以允许**一个**请求进入临界区的进程**立即**进入
2. **忙则等待**：当已有进程进入临界区时，其他试图进入临界区的进程**必须等待**
3. **有限等待**：对请求访问的进程，应保证能在**有限时间内**进入临界区（**不会饥饿**）
4. **让权等待**：当进程**不能进入**临界区时，应**立即释放处理器**，防止进程**忙等待**

📝 **真题（2020 年第 32 题）**：下列准则中，实现临界区互斥机制**必须遵循**的是：I. 两个进程不能同时进入临界区　II. 允许进程访问空闲的临界资源　III. 进程等待进入临界区的时间是有限的　IV. 不能进入临界区的执行态进程立即放弃 CPU
A. 仅 I、IV　B. 仅 II、III　C. 仅 I、II、III　D. 仅 I、III、IV
→ **C**
- I = 忙则等待，II = 空闲让进，III = 有限等待——这三条是**必须**遵循的
- IV = 让权等待——这一条是“**应该**”遵循的，但**不是必须**的（比如后面的 Peterson 算法、TSL 指令都不满足让权等待，但仍然能正确实现互斥）

🧒 **记忆口诀**：“**空闲让进，忙则等待，有限等待，让权等待**”——前三条保证正确，第四条提高效率。

## 二、软件实现方法（⭐⭐⭐）

以两个进程 P0 和 P1 为例。

### 📐 1. 单标志法
设一个公用整型变量 **turn**，表示**允许进入临界区的进程编号**。
```c
int turn = 0;     // 表示轮到谁进入

// P0：                          // P1：
while (turn != 0);  // 进入区    while (turn != 1);  // 进入区
critical section;               critical section;
turn = 1;           // 退出区    turn = 0;           // 退出区
remainder section;              remainder section;
```
- 两个进程**必须交替**进入临界区：P0 → P1 → P0 → P1……
- ✅ 满足**忙则等待**（同一时刻 turn 只有一个值）
- ❌ **违反“空闲让进”**：若 turn = 0 而 P0 不想进入临界区（一直在剩余区），那么 P1 即使想进入、临界区也空闲，**也进不去**
- 🧒 像两个人**轮流**用一个卫生间，规定“这次该你了”——如果轮到的人不去，另一个人憋着也不能进

### 📐 2. 双标志先检查法
设一个布尔数组 **flag[2]**，flag[i] = true 表示进程 Pi **想进入**（正在临界区）。
```c
bool flag[2] = {false, false};

// P0：                              // P1：
while (flag[1]);   // ① 先检查对方    while (flag[0]);   // ③
flag[0] = true;    // ② 再上锁        flag[1] = true;    // ④
critical section;                    critical section;
flag[0] = false;   // 解锁            flag[1] = false;
remainder section;                   remainder section;
```
- ✅ 不用交替进入，满足**空闲让进**
- ❌ **违反“忙则等待”**：若按 **① ③ ② ④** 的顺序执行——P0 检查 flag[1] = false，P1 检查 flag[0] = false，两者都认为对方不在，**同时进入临界区**！
- 原因：**“检查”和“上锁”两步不是原子的**，中间可能被打断

### 📐 3. 双标志后检查法
把“上锁”放到“检查”之前：
```c
// P0：                              // P1：
flag[0] = true;    // ① 先上锁        flag[1] = true;    // ③
while (flag[1]);   // ② 后检查        while (flag[0]);   // ④
critical section;                    critical section;
flag[0] = false;                     flag[1] = false;
remainder section;                   remainder section;
```
- ✅ 满足**忙则等待**（不会同时进入）
- ❌ **违反“空闲让进”和“有限等待”**：若按 **① ③ ② ④** 执行——两者都已上锁，然后都发现对方上了锁，**都进不去，互相无限等待**（产生**饥饿**/活锁现象）
- 🧒 两个人在门口，都举手说“我要进”，然后都看到对方举手，于是都谦让地等着……永远谁都不进

### 📐 4. Peterson 算法（⭐⭐⭐）
结合**单标志法的 turn**（谦让）和**双标志法的 flag**（表达意愿）：
```c
bool flag[2] = {false, false};   // 表示进入临界区的意愿
int turn = 0;                    // 表示优先让哪个进程进入

// P0：
flag[0] = true;                  // ① 表达自己想进入
turn = 1;                        // ② 主动谦让：让对方先进
while (flag[1] && turn == 1);    // ③ 对方也想进 且 最后是我谦让 → 等待
critical section;
flag[0] = false;                 // 退出：表示不再想进入
remainder section;

// P1：
flag[1] = true;                  // ④
turn = 0;                        // ⑤
while (flag[0] && turn == 0);    // ⑥
critical section;
flag[1] = false;
remainder section;
```
🧒 **比喻**：两个人在门口，都说“我想进”（flag），然后都客气地说“您先请”（turn = 对方）。**谁最后说“您先请”，谁就等着**；先说的那个人进去。

分析 ① ④ ② ⑤ ③ ⑥ 的执行顺序：
- P0、P1 都想进（flag 都为 true）
- P0 先让 turn = 1，然后 P1 让 turn = 0（**P1 最后谦让**）
- ③：P0 检查 flag[1] && turn == 1 → true && false = false → **P0 进入**
- ⑥：P1 检查 flag[0] && turn == 0 → true && true = true → **P1 等待** ✓

📐 **Peterson 算法满足**：**空闲让进、忙则等待、有限等待**；**不满足让权等待**（等待时 while 循环**忙等**，一直占用 CPU）

### 📐 软件方法小结
| 方法 | 空闲让进 | 忙则等待 | 有限等待 | 让权等待 | 问题 |
|---|---|---|---|---|---|
| 单标志法 | ❌ | ✅ | ✅ | ❌ | 必须交替进入 |
| 双标志先检查 | ✅ | ❌ | ✅ | ❌ | 可能同时进入 |
| 双标志后检查 | ❌ | ✅ | ❌ | ❌ | 可能都进不去（饥饿） |
| **Peterson** | ✅ | ✅ | ✅ | ❌ | 忙等 |

## 三、硬件实现方法（⭐⭐⭐）

软件方法的根本问题是：“检查”和“上锁”两步**不是原子的**。硬件方法直接从硬件上解决这个问题。

### 📐 1. 中断屏蔽方法（关中断）
CPU 只有在发生中断时才会进行进程切换。所以在进入临界区前**关中断**，退出后**开中断**，临界区执行期间就不会被切换：
```c
关中断;
临界区;
开中断;
```
- ✅ 简单、高效
- ❌ **不适用于多处理机**：关中断只对**执行关中断指令的那个 CPU** 有效，其他 CPU 上的进程仍可访问临界区
- ❌ **只适用于操作系统内核进程**，**不适用于用户进程**：开/关中断指令是**特权指令**，只能在内核态执行。而且如果让用户随意关中断，一个恶意程序关了中断不再打开，系统就瘫痪了
- ❌ 限制了 CPU 交替执行程序的能力，关中断时间过长会影响系统效率

### 📝 真题（2021 年第 45 题，7 分）⭐⭐⭐
> 下表给出了整型信号量 S 的 wait() 和 signal() 操作的功能描述，以及采用开/关中断指令实现信号量操作互斥的两种方法。
>
> | 功能描述 | 方法 1 | 方法 2 |
> |---|---|---|
> | `Semaphore S;` | `Semaphore S;` | `Semaphore S;` |
> | `wait(S) {`<br>`  while (S <= 0);`<br>`  S = S - 1;`<br>`}` | `wait(S) {`<br>`  关中断;`<br>`  while (S <= 0);`<br>`  S = S - 1;`<br>`  开中断;`<br>`}` | `wait(S) {`<br>`  关中断;`<br>`  while (S <= 0) {`<br>`    开中断;`<br>`    关中断;`<br>`  }`<br>`  S = S - 1;`<br>`  开中断;`<br>`}` |
> | `signal(S) {`<br>`  S = S + 1;`<br>`}` | `signal(S) {`<br>`  关中断;`<br>`  S = S + 1;`<br>`  开中断;`<br>`}` | `signal(S) {`<br>`  关中断;`<br>`  S = S + 1;`<br>`  开中断;`<br>`}` |
>
> 请回答下列问题。
> 1）为什么在 wait() 和 signal() 操作中对信号量 S 的访问必须互斥执行？
> 2）分别说明方法 1 和方法 2 是否正确。若不正确，请说明理由。
> 3）用户程序能否使用开/关中断指令实现临界区互斥？为什么？

**1）** 信号量 S 是**多个进程共享的变量**（临界资源），wait() 和 signal() 中对 S 的“读-判断-修改”不是原子操作。若不互斥，多个进程可能同时读到相同的 S 值并各自修改，导致 S 的值出错（例如两个进程同时通过 while(S <= 0) 的检查，都执行 S = S − 1，使本只够一个进程使用的资源被两个进程同时获得）。

**2）**
- **方法 1 错误**：在 wait() 中，若 S ≤ 0，进程会在**关中断的状态下**执行 while 死循环。由于中断被关闭，**时钟中断无法发生**，系统无法进行进程调度，**其他进程（包括要执行 signal(S) 的进程）永远得不到 CPU**，S 永远不会增加，于是该进程永远循环下去，**系统“卡死”**
- **方法 2 正确**：在 while 循环体内**先开中断再关中断**，给了系统响应中断、切换到其他进程的机会。其他进程可以执行 signal(S) 使 S 增大；而每次检查 S 和执行 S = S − 1 时都处于关中断状态，保证了互斥

**3）** **不能**。开/关中断指令是**特权指令**，只能在**内核态**执行，用户程序运行在用户态，无法执行。（而且若允许用户程序关中断，可能导致系统无法响应中断，影响系统安全和稳定。）

### 📐 2. TestAndSet 指令（TS / TSL 指令）
一条**原子操作**的硬件指令（执行过程不可被中断）：**读出**指定标志后，把该标志**设置为真**。用 C 描述其功能：
```c
bool TestAndSet(bool *lock) {   // 这整个函数是一条原子指令！
    bool old = *lock;           // 读出旧值
    *lock = true;               // 无论如何都上锁
    return old;                 // 返回旧值
}
```
用 TSL 实现互斥：
```c
bool lock = false;              // 共享变量，false 表示临界区空闲

while (TestAndSet(&lock));      // 进入区：上锁并检查
critical section;
lock = false;                   // 退出区：解锁
remainder section;
```
- 若 lock 原来是 false：TSL 返回 false，跳出循环进入临界区，同时 lock 已被置为 true
- 若 lock 原来是 true：TSL 返回 true，继续循环等待（置 true 不改变什么）
- ✅ **“检查”和“上锁”在一条原子指令中完成**，不会被打断
- ✅ 适用于**多处理机**环境（硬件保证对内存单元的原子访问，如锁总线）
- ✅ 简单
- ❌ **不满足“让权等待”**：暂时无法进入临界区的进程会占用 CPU 循环执行 TSL（**忙等**）

### 📐 3. Swap 指令（XCHG 指令）
**原子地交换**两个变量的内容：
```c
void Swap(bool *a, bool *b) {   // 原子指令
    bool temp = *a;
    *a = *b;
    *b = temp;
}
```
用 Swap 实现互斥：
```c
bool lock = false;              // 共享变量

// 每个进程：
bool key = true;                // 局部变量
while (key == true)
    Swap(&lock, &key);          // 交换后：lock 一定是 true，key 是 lock 原来的值
critical section;
lock = false;
remainder section;
```
- 逻辑与 TSL 完全相同：若 lock 原来是 false，交换后 key = false，退出循环进入临界区，lock 变为 true
- 优缺点与 TSL 相同：**原子**、适用多处理机、**不满足让权等待**

### 📝 真题（2023 年第 45 题，7 分）⭐⭐⭐
> 现要求学生使用 swap 指令和布尔型变量 lock 实现临界区互斥。lock 为线程间共享的变量。lock 的值为 TRUE 时线程不能进入临界区，为 FALSE 时线程能够进入临界区。某同学编写的实现临界区互斥的伪代码如下图 (a) 所示。
> ```c
> bool lock = FALSE;              // 共享变量
> ......
> bool key = TRUE;                //  ┐
> if (key == TRUE)                //  │ 进入区
>     swap key, lock;  // 交换 key 和 lock 的值
>                                 //  ┘
> 临界区;
> lock = TRUE;                    //  退出区
> ......
> ```
> 图 (b) 给出了交换两个变量值的函数 newSwap() 的代码：
> ```c
> void newSwap(bool *a, bool *b) {
>     bool temp = *a;
>     *a = *b;
>     *b = temp;
> }
> ```
> 请回答下列问题。
> (1) 图 (a) 的伪代码中哪些语句存在错误？将其改为正确的语句（不增加语句条数）。
> (2) 图 (b) 给出了交换两个变量值的函数 newSwap() 的代码，是否可以用函数调用语句“newSwap(&key, &lock)”代替指令“swap key, lock”以实现临界区互斥？为什么？

**(1)** 两处错误：
- **`if (key == TRUE)` 应改为 `while (key == TRUE)`**：用 if 只交换一次，若 lock 原来是 TRUE（有线程在临界区），交换后 key 仍为 TRUE，但 if 不会再判断，线程**照样进入临界区**，违反“忙则等待”。必须用 while 循环，直到 key 变为 FALSE 才能进入
- **退出区的 `lock = TRUE;` 应改为 `lock = FALSE;`**：退出临界区时要**解锁**，把 lock 置为 FALSE，否则其他线程永远无法进入

**(2)** **不能**。swap 指令是**原子**执行的（一条硬件指令，执行过程不会被中断）；而 newSwap() 是一个**函数**，编译后由**多条指令**组成，执行过程中**可能被中断**（发生线程切换）。例如：线程 A 执行 newSwap 时刚执行完 `temp = *a`（读到 lock = FALSE），就被切换；线程 B 也执行 newSwap 读到 lock = FALSE 并进入临界区；A 恢复后继续执行，也得到 key = FALSE 并进入临界区——**两个线程同时进入临界区**，无法实现互斥。

## 四、互斥锁（⭐）

### 📐 概念
**互斥锁（mutex lock）**：解决临界区最简单的工具。一个进程在进入临界区时**获得锁**，退出时**释放锁**。
```c
acquire() {                  // 获得锁（原子操作）
    while (!available);      // 忙等待
    available = false;       // 获得锁
}
release() {                  // 释放锁（原子操作）
    available = true;
}
```
- acquire() 和 release() 必须是**原子操作**，通常用 TSL 等硬件机制实现

### 📐 自旋锁
需要**连续循环忙等**的互斥锁（如用 TSL、Swap 实现的锁）称为**自旋锁（spin lock）**。
- ❌ **违反“让权等待”**，浪费 CPU
- ✅ 等待期间**不用切换进程上下文**。若上锁时间很短，自旋等待的代价比进程切换还小
- 常用于**多处理器系统**：一个核忙等，其他核上的进程可以很快释放锁
- **不太适用于单处理机系统**：忙等时，持有锁的进程无法运行，锁不可能在这个时间片内被释放，自旋毫无意义（只能等时间片用完）

## ⚠️ 易错点

1. **临界区是代码段**，临界资源是资源
2. **同步是直接制约**（合作、有顺序）；**互斥是间接制约**（竞争资源）
3. 必须遵循的准则：**空闲让进、忙则等待、有限等待**；**让权等待是“应该”但非“必须”**
4. 单标志法：违反**空闲让进**
5. 双标志先检查：违反**忙则等待**
6. 双标志后检查：违反**空闲让进**、**有限等待**（可能饥饿）
7. **Peterson 算法**：满足前三条，**不满足让权等待**
8. **中断屏蔽**：不适用于**多处理机**，不适用于**用户进程**（开关中断是特权指令）
9. **TSL、Swap**：原子指令，适用多处理机，**不满足让权等待**
10. 用函数模拟 Swap **不是原子的**，不能实现互斥
11. 关中断后死循环会导致**系统无法调度**

## 📋 本课小结

| 知识点 | 要点 |
|---|---|
| 临界资源/临界区 | 一次只能一个进程用的资源 / 访问它的代码 |
| 同步/互斥 | 直接制约（顺序）/ 间接制约（不同时） |
| 4 准则 | 空闲让进、忙则等待、有限等待、让权等待 |
| 软件方法 | 单标志、双标志先/后检查、Peterson（前三条都满足） |
| 硬件方法 | 关中断（单 CPU、内核）、TSL、Swap（原子、忙等） |
| 自旋锁 | 忙等，适合多处理器、短临界区 |

## 🏋️ 课后练习

1. 判断下列说法：(a) Peterson 算法满足让权等待；(b) 用关中断实现互斥在多处理机上也有效；(c) TestAndSet 指令执行时可以被中断；(d) 自旋锁适合单处理机系统。
2. 双标志先检查法中，为什么两个进程可能同时进入临界区？给出一种导致此结果的执行序列。
3. 以下代码试图用 TestAndSet 实现互斥，指出错误：
   ```c
   bool lock = false;
   while (!TestAndSet(&lock));
   critical section;
   lock = true;
   ```
4. 在 Peterson 算法中，若去掉 turn 变量（进入区只保留 `flag[i] = true; while (flag[j]);`），会变成哪种方法？有什么问题？
5. 为什么“让权等待”不是实现互斥所必须的准则？

<details>
<summary>📖 答案</summary>

1. (a) **错**（忙等）；(b) **错**；(c) **错**（原子指令）；(d) **错**（适合多处理机）
2. 因为“检查对方标志”与“设置自己标志”不是原子的。序列：P0 执行 `while(flag[1])`（flag[1] = false，通过）→ 切换到 P1 执行 `while(flag[0])`（flag[0] = false，通过）→ P1 执行 `flag[1] = true` 进入临界区 → 切换回 P0 执行 `flag[0] = true` 也进入临界区
3. 两处错误：① `while (!TestAndSet(&lock))` 应为 `while (TestAndSet(&lock))`——lock 原为 false 时返回 false，应该**跳出循环**进入临界区；② 退出区应为 `lock = false`（解锁）
4. 变成**双标志后检查法**。若两个进程先后都执行了 `flag[i] = true`，再去检查对方，会发现对方的 flag 都为 true，于是**都在 while 中等待，谁也进不去**，违反“空闲让进”和“有限等待”。turn 变量的作用正是打破这种僵局：两者都想进时，“最后谦让的一方”等待，另一方进入
5. 让权等待只是为了**避免忙等、提高 CPU 利用率**，并不影响互斥的**正确性**。不满足它（如 Peterson、TSL）也能正确实现互斥，只是浪费 CPU 时间
</details>
