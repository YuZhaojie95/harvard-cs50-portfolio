## 一、TCP 的特点（⭐⭐）

1. TCP 是**面向连接**（虚连接）的传输层协议
2. 每一条 TCP 连接**只能有两个端点**，每一条 TCP 连接**只能是点对点**的（一对一）
3. TCP 提供**可靠交付**的服务：**无差错、不丢失、不重复、按序到达**（可靠有序，不丢不重）
4. TCP 提供**全双工**通信：发送缓存（准备发送的数据 & 已发送但尚未收到确认的数据）、接收缓存（按序到达但尚未被接收应用程序读取的数据 & 不按序到达的数据）
5. TCP **面向字节流**：TCP 把应用程序交下来的数据看成仅仅是一连串的**无结构的字节流**
   - 流：流入到进程或从进程流出的字节序列
   - TCP 不关心应用层报文的边界，它根据对方给出的窗口值和当前网络拥塞程度来决定一个报文段应包含多少个字节

## 二、TCP 报文段首部格式（⭐⭐⭐）

TCP 报文段 = 首部（**固定 20B** + 选项，最长 **60B**）+ 数据部分
```
 0                     16                              31
 ┌──────────────────────┬──────────────────────────────┐
 │       源端口（16）      │        目的端口（16）            │
 ├──────────────────────┴──────────────────────────────┤
 │                   序号 seq（32）                       │
 ├─────────────────────────────────────────────────────┤
 │                 确认号 ack（32）                        │
 ├──────┬──────┬─┬─┬─┬─┬─┬─┬───────────────────────────┤
 │数据偏移│ 保留  │U│A│P│R│S│F│       窗口（16）            │
 │ (4)  │ (6)  │R│C│S│S│Y│I│                           │
 │      │      │G│K│H│T│N│N│                           │
 ├──────┴──────┴─┴─┴─┴─┴─┴─┴───────────────────────────┤
 │       检验和（16）       │       紧急指针（16）            │
 ├──────────────────────┴──────────────────────────────┤
 │                选项（长度可变）              │  填充     │
 └─────────────────────────────────────────────────────┘
```

| 字段 | 长度 | 含义 |
|---|---|---|
| 源端口、目的端口 | 各 2B | |
| **序号 seq** | 4B | 在一个 TCP 连接中传送的字节流中的每一个字节都按顺序编号，本字段表示**本报文段所发送数据的第一个字节的序号** |
| **确认号 ack** | 4B | **期望收到对方下一个报文段的第一个数据字节的序号**。若确认号为 N，则证明到序号 **N − 1 为止的所有数据都已正确收到**（**累积确认**） |
| **数据偏移（首部长度）** | 4 位 | TCP 报文段的数据起始处距离 TCP 报文段的起始处有多远，即**首部长度**，以 **4B 为单位**（最大 15 × 4 = 60B） |
| 保留 | 6 位 | 保留为今后使用，目前置 0 |
| **URG**（紧急位） | 1 位 | URG = 1 时，表明此报文段中有**紧急数据**，是高优先级的数据，应尽快传送，**不用在缓存里排队**，配合**紧急指针**字段使用 |
| **ACK**（确认位） | 1 位 | ACK = 1 时**确认号有效**。在连接建立后所有传送的报文段都必须把 ACK 置为 1 |
| **PSH**（推送位） | 1 位 | PSH = 1 时，接收方**尽快交付**接收应用进程，不再等到缓存填满再向上交付 |
| **RST**（复位位） | 1 位 | RST = 1 时，表明 TCP 连接中出现**严重差错**，必须**释放连接**，然后再重新建立传输链接 |
| **SYN**（同步位） | 1 位 | SYN = 1 时，表明是一个**连接请求/连接接受**报文 |
| **FIN**（终止位） | 1 位 | FIN = 1 时，表明此报文段发送方数据已发完，要求**释放连接** |
| **窗口** | 2B | 指的是**发送本报文段的一方的接收窗口**，即现在允许对方发送的数据量（**流量控制**） |
| **检验和** | 2B | 检验**首部 + 数据**，检验时要加上 **12B 伪首部**（协议号 **6**） |
| 紧急指针 | 2B | URG = 1 时才有意义，指出本报文段中紧急数据的字节数（紧急数据在报文段数据的最前面） |
| **选项** | 最长 40B | 如**最大报文段长度 MSS**（TCP 报文段中**数据字段**的最大长度，不含首部）、窗口扩大、时间戳、选择确认（SACK） |

⚠️ 关键点：
- **序号是按字节编号的**，不是按报文段编号
- **SYN 和 FIN 报文段即使不携带数据，也要消耗一个序号**
- **纯 ACK 报文段**（不带数据）**不消耗序号**
- **MSS 指数据部分的最大长度**（不含 TCP 首部和 IP 首部）

✏️ **例**：主机甲发送了两个连续的报文段，序号分别为 70 和 100。
- 第一个报文段携带了 100 − 70 = **30B** 数据
- 乙收到第一个报文段后发回的确认号应是 **100**
- 若乙收到第二个报文段后发回的确认中确认号为 180，则第二个报文段携带了 180 − 100 = **80B**
- 若第一个报文段丢失，第二个到达，乙发回的确认号是 **70**（累积确认：期望收到的仍然是 70）

## 三、TCP 连接管理（⭐⭐⭐）

### 📐 TCP 连接的建立（三次握手）
假设客户端 A 主动打开连接，服务器 B 被动打开（处于 **LISTEN** 状态）。
```
      客户端 A                                        服务器 B
   CLOSED                                          LISTEN
      │ ① SYN = 1, seq = x                           │
      │ ───────────────────────────────────────────► │
 SYN-SENT                                             │
      │ ② SYN = 1, ACK = 1, seq = y, ack = x + 1     │
      │ ◄─────────────────────────────────────────── │ SYN-RCVD
      │ ③ ACK = 1, seq = x + 1, ack = y + 1          │
      │ ───────────────────────────────────────────► │
 ESTABLISHED                                     ESTABLISHED
```
1. **第一次握手**：客户端发送**连接请求报文段**，无应用层数据。**SYN = 1，seq = x**（随机）。客户端进入 **SYN-SENT** 状态
2. **第二次握手**：服务器端为该 TCP 连接**分配缓存和变量**，并向客户端返回**确认报文段**，允许连接，无应用层数据。**SYN = 1，ACK = 1，seq = y**（随机），**ack = x + 1**。服务器进入 **SYN-RCVD** 状态
3. **第三次握手**：客户端为该 TCP 连接**分配缓存和变量**，并向服务器端返回确认的确认，**可以携带数据**。**SYN = 0，ACK = 1，seq = x + 1，ack = y + 1**。双方进入 **ESTABLISHED** 状态

⚠️ 注意：
- 第一、二次握手报文段**不能携带数据**（SYN = 1），但要**消耗一个序号**
- 第三次握手的报文段**可以携带数据**；若**不携带数据则不消耗序号**（下一个报文段的 seq 仍是 x + 1）
- **SYN 洪泛攻击**：攻击者发送大量 SYN，但不回复第三次握手，使服务器维持大量“半连接”（SYN-RCVD），资源耗尽。防御：SYN cookie

📐 **为什么是三次握手，不是两次？**
为了防止**已失效的连接请求报文段**突然又传到了服务器，因而产生错误。
- 若只有两次握手：客户端的一个旧 SYN 在网络中滞留，客户端早就放弃了，这个旧 SYN 迟到后到达服务器，服务器以为是新的连接请求，回复确认后就建立连接、分配资源——但客户端根本不理它，**服务器的资源白白浪费**
- 三次握手中，服务器要等客户端的第三次确认才建立连接，客户端对旧 SYN 的确认不会回复，连接就不会建立

### 📐 TCP 连接的释放（四次挥手）
参与一条 TCP 连接的两个进程中的**任何一个都能终止**该连接。假设客户端 A 先主动关闭：
```
      客户端 A                                        服务器 B
 ESTABLISHED                                     ESTABLISHED
      │ ① FIN = 1, seq = u                           │
      │ ───────────────────────────────────────────► │
 FIN-WAIT-1                                           │
      │ ② ACK = 1, seq = v, ack = u + 1              │
      │ ◄─────────────────────────────────────────── │ CLOSE-WAIT
 FIN-WAIT-2                                           │ （B 还可以继续发数据：半关闭）
      │ ③ FIN = 1, ACK = 1, seq = w, ack = u + 1     │
      │ ◄─────────────────────────────────────────── │ LAST-ACK
 TIME-WAIT                                            │
      │ ④ ACK = 1, seq = u + 1, ack = w + 1          │
      │ ───────────────────────────────────────────► │
      │                                              │ CLOSED
      │ 等待 2MSL                                     
 CLOSED
```
1. **第一次挥手**：客户端发送**连接释放报文段**，停止再发送数据，主动关闭 TCP 连接。**FIN = 1，seq = u**。客户端进入 **FIN-WAIT-1**
2. **第二次挥手**：服务器端回送一个**确认报文段**，客户到服务器这个方向的连接就释放了——**半关闭**状态。**ACK = 1，seq = v，ack = u + 1**。服务器进入 **CLOSE-WAIT**；客户端收到后进入 **FIN-WAIT-2**
   - 此时服务器**还可以继续向客户端发送数据**
3. **第三次挥手**：服务器端发完数据，就发出**连接释放报文段**，主动关闭 TCP 连接。**FIN = 1，ACK = 1，seq = w，ack = u + 1**。服务器进入 **LAST-ACK**
4. **第四次挥手**：客户端回送一个确认报文段，再**等待计时器设置的 2MSL**（最长报文段寿命）后，连接彻底关闭。**ACK = 1，seq = u + 1，ack = w + 1**。客户端进入 **TIME-WAIT**，服务器收到后进入 **CLOSED**

⚠️ 注意：
- **FIN 报文段即使不携带数据，也消耗一个序号**
- 若服务器没有数据要发了，第二、三次挥手可以**合并**（FIN + ACK 一起发）

📐 **为什么客户端要等待 2MSL？（⭐⭐⭐）**
**MSL（Maximum Segment Lifetime）**：最长报文段寿命，报文段在网络中存活的最长时间。
1. **保证 A 发送的最后一个 ACK 能够到达 B**：如果这个 ACK 丢失，B 会超时重传 FIN，A 在 2MSL 内能收到重传的 FIN，并重新发送 ACK
2. **防止已失效的连接请求报文段出现在本连接中**：经过 2MSL，本连接持续的时间内所产生的所有报文段都从网络中消失，下一个新连接中不会出现旧的报文段

📝 **真题（2021 年第 38 题）**：若客户首先向服务器发送 FIN 段请求断开 TCP 连接，则当客户收到服务器发送的 FIN 段并向服务器发送了 ACK 段后，客户的 TCP 状态转换为：A. CLOSE_WAIT　B. TIME_WAIT　C. FIN_WAIT_1　D. FIN_WAIT_2
→ **B**（主动关闭方收到对方 FIN 并回 ACK 后进入 **TIME_WAIT**）

📝 **真题（2022 年第 39 题）**：假设客户 C 和服务器 S 已建立一个 TCP 连接，通信往返时间 RTT = 50ms，最长报文段寿命 MSL = 800ms，数据传输结束后，C 主动请求断开连接。若从 C 主动向 S 发出 FIN 段时刻算起，则 C 和 S 进入 CLOSED 状态所需的时间至少分别是：A. 850ms, 50ms　B. 1650ms, 50ms　C. 850ms, 75ms　D. 1650ms, 75ms
- 单程时延 = RTT / 2 = 25ms
- t = 0：C 发 FIN
- t = 25ms：S 收到 FIN，**立即**发送 ACK + FIN（合并第二、三次挥手，时间最少）
- t = 50ms：C 收到 FIN，发送 ACK，进入 TIME_WAIT，**等 2MSL = 1600ms** → C 在 **1650ms** 进入 CLOSED
- t = 75ms：S 收到最后的 ACK，进入 **CLOSED**
→ 选 **D**

📝 **真题（2020 年第 39 题）**：若主机甲与主机乙建立 TCP 连接时，发送的 SYN 段中的序号为 1000，在断开连接时，甲发送给乙的 FIN 段中的序号为 5001，则在无任何重传的情况下，甲向乙已经发送的应用层数据的字节数为：A. 4002　B. 4001　C. 4000　D. 3999
- SYN 段序号 1000，**SYN 消耗 1 个序号**，所以数据从 **1001** 开始
- FIN 段序号 5001，说明数据的最后一个字节是 **5000**
- 数据字节数 = 5000 − 1001 + 1 = **4000** → 选 **C**

### 📐 TCP 状态速查
| 状态 | 含义 |
|---|---|
| LISTEN | 服务器等待连接请求 |
| SYN-SENT | 客户端已发 SYN，等待确认 |
| SYN-RCVD | 服务器已收到 SYN 并回复，等待确认 |
| ESTABLISHED | 连接已建立 |
| FIN-WAIT-1 | 主动关闭方已发 FIN |
| FIN-WAIT-2 | 主动关闭方收到对 FIN 的 ACK，等对方的 FIN |
| CLOSE-WAIT | 被动关闭方收到 FIN，等待自己的应用关闭 |
| LAST-ACK | 被动关闭方已发 FIN，等待最后的 ACK |
| **TIME-WAIT** | 主动关闭方已回复最后的 ACK，**等待 2MSL** |
| CLOSED | 连接关闭 |

## 四、TCP 可靠传输（⭐⭐⭐）

### 📐 可靠传输的机制
**可靠**：保证接收方进程从缓存区读出的字节流与发送方发出的字节流**完全一样**。TCP 实现可靠传输的机制：
1. **校验**：与 UDP 校验一样，增加伪首部
2. **序号**：一个字节占一个序号，序号字段指的是一个报文段第一个字节的序号
3. **确认**：TCP 默认使用**累积确认**
4. **重传**：**超时重传**、**快速重传**

### 📐 超时重传与 RTO（⭐⭐）
TCP 发送方在规定的时间内**没有收到确认**就要**重传**已发送的报文段。
- **重传时间 RTO** 的设置：TCP 采用**自适应算法**，动态改变重传时间 RTTs（**加权平均往返时间**）
```
新的 RTTs = (1 − α) × 旧的 RTTs + α × 新的 RTT 样本      （α 推荐 1/8）
新的 RTT_D = (1 − β) × 旧的 RTT_D + β × |RTTs − 新的 RTT 样本|   （β 推荐 1/4）
RTO = RTTs + 4 × RTT_D
```
- RTO 应**略大于** RTTs
- **Karn 算法**：在计算加权平均 RTTs 时，只要报文段**重传**了，就**不采用其往返时间样本**（因为不知道确认是针对原报文段还是重传报文段）；且报文段每重传一次，就把 RTO **增大一倍**（通常是 2 倍）

✏️ **例**：设 α = 1/8，当前 RTTs = 30ms，新测得的 RTT 样本为 26ms、32ms、24ms（依次），求新的 RTTs。
- 第 1 次：RTTs = 7/8 × 30 + 1/8 × 26 = 26.25 + 3.25 = **29.5ms**
- 第 2 次：RTTs = 7/8 × 29.5 + 1/8 × 32 = 25.8125 + 4 = **29.8125ms**
- 第 3 次：RTTs = 7/8 × 29.8125 + 1/8 × 24 ≈ 26.0859 + 3 = **29.0859ms**

### 📐 快速重传（⭐⭐）
超时触发重传存在的问题：**超时周期往往太长**。
- 发送方通常可以在超时事件发生之前通过注意所谓**冗余 ACK** 来较好地检测丢包情况
- **冗余 ACK（重复确认）**：TCP 规定每当比期望序号大的**失序报文段**到达时，发送一个冗余 ACK，**指明下一个期待字节的序号**
- 发送方收到对同一个报文段的 **3 个冗余 ACK**（即共收到 4 个相同的 ACK），就可以认为跟在这个被确认报文段之后的报文段已经**丢失**，**立即重传**（不必等超时）

✏️ 发送方已发送 1、2、3、4、5 号报文段，其中 2 号丢失：
- 接收方收到 1 → ACK 2
- 收到 3（失序）→ **ACK 2**（冗余 1）
- 收到 4（失序）→ **ACK 2**（冗余 2）
- 收到 5（失序）→ **ACK 2**（冗余 3）
- 发送方收到 3 个冗余 ACK → **立即重传 2 号**报文段

### 📐 TCP 的确认特点
- **累积确认**：确认号 N 表示 N 之前的所有字节都已收到
- **捎带确认**：接收方有数据要发送时，把确认信息顺便放在数据报文段中
- **推迟确认**：接收方可以推迟发送确认（但不超过 0.5 秒），以减少确认报文段的数量
- 对于失序到达的报文段，TCP 标准**没有规定**如何处理，通常**缓存**起来（类似 SR），但确认仍是**累积确认**

## ⚠️ 易错点

1. TCP 首部**固定 20B**，最长 60B；**数据偏移单位 4B**
2. **序号按字节编号**；确认号 = **期望收到的下一个字节的序号**
3. **SYN、FIN 消耗一个序号**；纯 ACK 不消耗
4. 三次握手：**SYN（seq=x）→ SYN+ACK（seq=y, ack=x+1）→ ACK（seq=x+1, ack=y+1）**
5. 第三次握手**可以携带数据**
6. 四次挥手：**主动关闭方**经过 FIN-WAIT-1 → FIN-WAIT-2 → **TIME-WAIT（2MSL）** → CLOSED
7. **被动关闭方**：CLOSE-WAIT → LAST-ACK → CLOSED
8. 求“最少时间”时，被动方的 **ACK 和 FIN 可以合并**
9. **数据字节数 = FIN 序号 − (SYN 序号 + 1)**
10. RTO = RTTs + 4RTT_D；**重传的报文段不计入 RTT 样本**（Karn）
11. **3 个冗余 ACK** 触发快速重传
12. **MSS 是数据部分**的最大长度

| 三次握手 | SYN → SYN+ACK → ACK；防止旧请求 |
| 四次挥手 | FIN → ACK → FIN → ACK；TIME-WAIT 2MSL |
| 可靠传输 | 序号、累积确认、超时重传（RTO 自适应）、快速重传（3 冗余 ACK） |

## 🏋️ 课后练习

1. 主机 A 向 B 发起 TCP 连接，A 的初始序号为 100，B 的初始序号为 500。写出三次握手中各报文段的 SYN、ACK 标志以及 seq、ack 的值。若随后 A 发送 200B 数据，该报文段的 seq 是多少？B 的确认号是多少？
2. 为什么 TIME-WAIT 状态要等待 2MSL？
3. 设 MSL = 1 分钟，主动关闭方在收到对方的 FIN 并发送 ACK 后，至少还要等多久才能释放连接？
4. TCP 的确认号为 1000，窗口为 2000，表示什么？
5. 判断：(a) TCP 的序号是对报文段编号的；(b) 第三次握手的报文段不能携带数据；(c) 快速重传要等到超时后才重传。

<details>
<summary>📖 答案</summary>

1. ① SYN = 1，ACK = 0，seq = **100**；② SYN = 1，ACK = 1，seq = **500**，ack = **101**；③ SYN = 0，ACK = 1，seq = **101**，ack = **501**。之后 A 发送 200B 数据：seq = **101**（第三次握手不带数据，不消耗序号），B 的确认号 = 101 + 200 = **301**
2. ① 保证最后一个 ACK 能到达对方，若丢失可以在 2MSL 内收到对方重传的 FIN 并重发 ACK；② 使本连接中产生的所有报文段都从网络中消失，避免旧报文段干扰下一个新连接
3. **2 分钟**
4. 发送该报文段的一方已正确收到对方序号 999 及以前的所有数据，期望收到从 **1000** 开始的数据，并且允许对方再发送 **2000B**（序号 1000~2999）
5. (a) **错**，按字节编号；(b) **错**，可以携带；(c) **错**，收到 3 个冗余 ACK 就立即重传，不等超时
</details>
